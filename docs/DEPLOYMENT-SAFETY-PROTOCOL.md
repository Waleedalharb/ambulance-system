# بروتوكول أمان النشر — منصة الجنوب (Deployment Safety Protocol)

> معتمد في A-3.6 (2026-10-04). هذا المستند **إلزامي** لأي تعديل كبير على المنصة،
> والغاية منه منع تكرار المشاكل التاريخية: اختلاف البيانات بين SQLite وJSON،
> الإشعارات الصامتة، وتعدد مصادر الحقيقة.

---

## 1) دورة الحياة الإلزامية لأي تعديل

```
ANALYSIS → IMPLEMENT → TEST → REVIEW → APPROVE → DEPLOY → POST-DEPLOY VERIFY
```

| المرحلة | القاعدة |
|---|---|
| ANALYSIS | تحليل فقط: فحص الكود + بيانات الإنتاج (READ-ONLY) + تقرير. أي تعارض أو غموض يُعرض كقرار مستقل ولا يُحسم ذاتيًا. |
| IMPLEMENT | لا يبدأ إلا باعتماد صريح مكتوب من مالك المنصة. نطاق محدد حرفيًا؛ ما خرج عن النطاق لا يُمسّ. |
| TEST | اختبار معزول مخصص للبند (بيئة VACUUM مؤقتة، لا تلمس بيانات حقيقية) + الانحدار الكامل + مقارنة الـ baseline. |
| REVIEW | تقرير تنفيذ كامل: الملفات، الـ diff، نتائج الاختبارات، الانحدار، المخاطر، git status. |
| APPROVE | قبول مكتوب من المالك. **القبول التقني ≠ موافقة النشر** — النشر قرار مستقل. |
| DEPLOY | لا يتم إلا بعد `GATE: PASS` وموافقة نشر صريحة. |
| POST-DEPLOY VERIFY | Smoke للإنتاج + مراقبة سجلات Render. "Deploy successful" من Render **وحدها ليست نجاحًا**. |

**ممنوع القفز:** `IMPLEMENT → PUSH → DEPLOY` ثم اكتشاف المشكلة — هذا النمط محظور نهائيًا.

## 2) بوابة ما قبل النشر (Pre-Deploy Gate)

الأمر:

```bash
node scripts/pre-deploy-gate.js --target scripts/<اختبار-البند>.js
```

البنود الـ 11 الإلزامية:

1. **Git status** — توثيق المتغير + رفض أي تعديل على ملفات محظورة (`db/database.js`, `db/migrate.js`).
2. **Targeted tests** — اختبار البند المعزول يمرّ بالكامل (يُحدَّد صراحة بـ `--target`).
3. **Full regression** — `scripts/run-regression-isolated.js`.
4. **Baseline comparison** — `167 ✅` على الأقل + صفر إخفاقات جديدة خارج القائمة المعروفة العشر + تعطل `EMPTY_PERIODS_GUARD` المعروف.
5. **SQLite schema** — الجداول المطلوبة موجودة + `quick_check=ok` + كشف المخططات التاريخية.
6. **Migration inspection** — كل `CREATE TABLE` محمي بـ `IF NOT EXISTS`، وكل `DROP TABLE` داخل إعادة بناء محروسة (`foreign_keys=OFF` + معاملة).
7. **JSON fallback detection** — قرّاء المخازن المُرحَّلة (`readAnnouncements`/`readShifts`/`readPeakData`) لا يلمسون JSON إطلاقًا.
8. **API contract check** — المسارات ومحوّلات العقد موجودة حرفيًا.
9. **Frozen JSON protection** — صفر كتابات على ثوابت مسارات الملفات المجمّدة.
10. **Boot check** — إقلاع نظيف على نسخة معزولة.
11. **/health** — استجابة 200 + `status=ok`.

**القاعدة:** المخرجة `GATE: PASS` أو `GATE: FAIL` مع السبب. **لا نشر قبل PASS كامل.**

### الـ baseline الثابت

- `167` ناجحًا — لا يقبل أقل.
- 10 إخفاقات معروفة مسماة: W1-B ①②④، V-B ⑪⑫②④②⑦، F6 ④، SR-1 ①⑨.
- تعطل `EMPTY_PERIODS_GUARD` في roster-sync معروف ومستقل.
- **أي إخفاق جديد = FAIL** حتى لو بقي العدد 167.
- تحديث الـ baseline نفسه يحتاج قرار مالك مستقل.

## 3) Smoke الإنتاج (Post-Deploy)

**القاعدة الذهبية: Production Smoke = READ-ONLY افتراضيًا.**

- ممنوع في الـ smoke: `POST/PUT/PATCH/DELETE` على الموارد، `INSERT/UPDATE/DELETE` على القاعدة، إنشاء بيانات تجريبية، أي بث تجريبي للمشغلين.
- الاستثناء الموثق الوحيد: المصادقة (يفضَّل `SMOKE_TOKEN`؛ تسجيل الدخول ببيانات اعتماد مسموح كما في الـ smokes التاريخية).
- **اختبارات الكتابة على الإنتاج ليست جزءًا من الـ smoke إطلاقًا** — أي Production write test يحتاج **موافقة مستقلة مكتوبة** تحدد: البيانات، البث المتوقع للشاشات الحية، وخطة التنظيف.
- النجاح يتطلب: Smoke PASS + سجلات Render نظيفة بعد النشر (لا أخطاء هجرة/إقلاع).

### smoke الخاص بـ A-3.5

```bash
# من أي مكان (فحوص API):
set SMOKE_TOKEN=<jwt> && node scripts/peak-production-smoke.js

# داخل Render Shell (يضيف SQLite + الملف المجمّد):
DB_PATH=/data/ambulance.db DATA_DIR=/data node scripts/peak-production-smoke.js

# للمقارنة حقل-بحقل مع النسخة المجمّدة: احفظ ناتج cat /data/peak-data.json في
# test-output/peak-frozen-backup.json أو وفّر PEAK_FROZEN_BACKUP=<مسار>

# تحقق ذاتي محلي معزول (قبل النشر):
node scripts/peak-production-smoke.js --self-test
```

يتحقق من: `/health`، بنية `/api/peak-data`، الأعداد (3/3/6)، المطابقة حقل-بحقل مع النسخة المجمّدة، IDs، الترتيب، الحالات، missionId، radius=5000، صفر أيتام، عقد camelCase، سلامة `peak_plans`، سلامة `peak-data.json` المجمّد، وغياب أخطاء الهجرة.

## 4) حماية النسخ المجمّدة (Frozen Backups)

- ملفات JSON للمخازن المُرحَّلة (`announcements.json`, `shift-data.json`, `peak-data.json`) **لا تُحذف ولا تُعدَّل أبدًا** — هي خط الرجوع الأخير.
- الزرع منها يحدث **مرة واحدة فقط** عند الجداول الفارغة (داخل `db.js` migrations)، وهو idempotent.
- أي كود يكتب عليها يُعتبر عطلًا حرجًا — البوابة تفحص ذلك آليًا (البند 9).

### تطبيع نوعي معتمد: lat/lng (قرار المالك — A-3.5)

- في Frozen JSON التاريخي (`peak-data.json`) تُخزَّن `lat`/`lng` **كنصوص** (`"24.6929571930255"`).
- SQLite يخزّنها كـ `REAL`، والـ API بعد الترحيل يعيدها **كأرقام**.
- هذا **تطبيع نوعي مقصود ومعتمد**: لا يغيّر القيمة الجغرافية إطلاقًا، والمقارنة في الـ smoke رقمية بتفاوت `±1e-9` — اختلاف String/Number وحده ليس فشلًا، واختلاف القيمة الفعلي فشل.
- **بقية حقول الـ API كلها تحافظ على العقد الحالي حرفيًا** (أسماءً وأنواعًا وترتيبًا) — لا تطبيع آخر بلا قرار مستقل.

## 5) ضوابط الـ migrations

- كل هجرة idempotent (قابلة لإعادة التنفيذ بلا أثر).
- `CREATE TABLE` دائمًا مع `IF NOT EXISTS`؛ تغيير المخطط فقط عبر نمط إعادة البناء المحروس (`foreign_keys=OFF` + معاملة واحدة + نسخ حرفي للصفوف).
- لا `DROP` لجدول يحمل بيانات إنتاجية خارج إعادة بناء موثقة. الاستثناءات التاريخية المعتمدة (مثل `daily_reports` في F4) تُدار حصريًا عبر سجل `APPROVED_DROP_EXCEPTIONS` في `scripts/pre-deploy-gate.js` — وأي استثناء جديد يحتاج قرار مالك موثقًا بالسبب والتاريخ.
- فحص التكامل المرجعي قبل زرع البيانات المترابطة (مثال A-3.5: تنبيه يتيم ⇒ إيقاف كامل + تبليغ، لا حذف ولا إصلاح تلقائي).
- البيانات الإنتاجية تُقارن على Render (READ-ONLY) قبل أي ترحيل — لا قرارات على البيانات المحلية.

## 6) الممنوعات الدائمة أثناء دورات العمل

- `git reset` / `git clean` / `git stash` — حمايةً للتعديلات المحلية القائمة.
- `commit` / `push` / `merge` / `PR` / `deploy` — إلا بأمر مستقل صريح من المالك.
- حذف أو تعديل أي ملف بيانات إنتاجي.
- الالتفاف على فشل اختبار بتعديل `node_modules` أو بيئة التشغيل.
